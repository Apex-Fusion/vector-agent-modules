# Module-6 identity checks and their tests

Source of truth:

- Part 2 (`docs/IDENTITY_REGISTRY.md` in agents-marketplace): §7 (Module-6 row, Time rule), §3.10 (library), §12.1 (test style).
- Part 1 (`docs/did-vector-method.md`): §5 (record format), §7.3 (effective status).

## Where the check is

`utils.agent_record(config, agent_did, agent_credential, w, reference_inputs, signatories)` holds the identity check. `utils.verify_active_agent` takes the same arguments and is `True` when `agent_record` returns a record. The caller first gets the window `w` from `shared/identity.window(tx.validity_range)` and fails without it. The record is returned only when all of these are true:

1. `shared/identity.window(validity_range)` is `Some(w)`: both bounds are finite, `lo <= hi` and `hi - lo <= 3_600_000`.
2. `shared/identity.active_record(reference_inputs, config.identity_hash, agent_did, w)` is `Some(record)`: `vector_identity.find_record` finds the record, and `vector_identity.effective` over `[w.lo, w.hi]` is `EffActive`.
3. `shared/identity.declared_credential(record, agent_credential)`: the credential is `VerificationKey(h)`, and `h` is `blake2b_224(controller)` or the hash of a listed key with the transaction purpose.
4. `shared/credential.verify_signer(agent_credential, signatories)`: the key `h` signed.

With the transaction's reference inputs, signatories and validity range, this is `shared/identity.credential_opens`.

The checks read the datum of the new position, not the datum of the spent UTxO:

| Action (redeemer) | Function | Datum that the checks read | Agent and credential | Place in the result |
|---|---|---|---|---|
| SubmitProposal (`proposal_spend`) | `proposal_validation.validate_submit_proposal` | the output with the new proposal token `proposal_token_name(own_ref)` | `proposer_did`, `proposer_credential` | first check, `fail @"FAIL:identity_valid"` |
| AmendProposal (`proposal_spend`) | `proposal_validation.validate_amend_proposal` | the new datum that the continuing output must carry | `proposer_did`, `proposer_credential` | a conjunct of the result |
| MintCritiqueToken (`critique_spend`) | `critique_validation.validate_submit_critique` | the output with the new critique token `critique_token_name(own_ref)` | `critic_did`, `critic_credential` | `agent_record`, then the other conjuncts |
| MintEndorsementToken (`endorsement_spend`) | `critique_validation.validate_submit_endorsement` | the output with the endorsement token of the spent datum | `endorser_did`, `endorser_credential` | `agent_record`, then the other conjuncts |

Each validator passes `tx.reference_inputs`, `tx.extra_signatories` and the window of `tx.validity_range`. The check is a part of the Bool result of each of the four redeemers, so the optimizer cannot move it into another branch. `GovernanceConfig` has `identity_hash` as its last (11th) field. The legacy fields `registry_policy_id` and `registry_script_hash` are removed. No Module-6 file imports `shared/did_verification`.

## Where each `fail` test fails

`aiken check` prints the traces of each `fail` test. They show:

- All `submit_proposal_*_fails` tests except two fail at `FAIL:identity_valid`. The identity check is the first check of `validate_submit_proposal`. `submit_proposal_check_rejects_range_without_lower_bound` also fails at `FAIL:identity_valid`.
- `submit_proposal_range_without_lower_bound_fails` and `amend_proposal_range_without_lower_bound_fails` fail at `expect Some(current_slot) = get_lower_bound_slot(tx)` in `proposal_spend`. This existing statement runs before the redeemer branch. The two `*_check_rejects_range_without_lower_bound` tests show that the identity check alone also rejects that range.
- All four `X_subagent_without_parent_fails` tests fail at `expect Some(parent_record) = find_record(refs, identity_hash, parent)` in `vector_identity.effective`.

The negative tests that use `!handler(...)` get `False` from the handler. A mutation run checked that the identity check gives this `False` (see the section "Mutation runs").

## Decisions

- **AmendProposal has the identity check.** An amendment is an action of the proposer on its open position, and it changes the position. It uses the `proposer_did` and the `proposer_credential` of the spent proposal. The continuing output keeps both fields (an existing rule).
- **The signature is part of the identity check.** `verify_active_agent` also checks the signature, like `shared/identity.credential_opens`. The existing `signer_valid` checks stay unchanged. They are now redundant for these four actions.
- **No capability check.** The Module-6 row names no capability. Module-3 checks capabilities; Module-6 does not.
- **Subagents can act.** A subagent passes when each ancestor record is a reference input, each ancestor is Active over the range and no parent increased its subagent epoch. The Module-6 row has no subagent rule.
- **The status covers the whole range.** A hold in force at `lo`, or an Accountable Party that ends before `hi`, rejects the action.
- **No identity check on the other redeemers.** WithdrawProposal, WithdrawCritique and WithdrawEndorsement are exits. Adopt, Reject, ExtendReview (Foundation), Expire, ExpireStale (anybody), SpendActivity, IncorporateCritique, RewardCritique, BurnCritiqueToken, BurnEndorsementToken and the two mint policies settle positions or follow another action. The agent that owns the position does not act in them. So stakes and rewards go back whatever the agent's status, and a suspended, revoked or retired agent can always exit. This is the safest choice for funds.
- **No time rule on the other redeemers.** They read no identity record. `proposal_spend` still needs a finite lower bound for every redeemer (an existing rule).
- **P-256 keys never count.** A P-256 key with the transaction bit is rejected. The registry does not accept such a key, and the module does not depend on that rule.
- **Trace name.** `FAIL:did_valid` is now `FAIL:identity_valid`.

### Decisions

- **proposal_ref is the seed.** A critique or endorsement names its proposal by the seed: the output reference that SubmitProposal spent. The proposal token is `proposal_token_name(seed)`, and it stays with the proposal through amendments and extensions. No UTxO keeps the output reference of the seed after the submission, so "the input with that output reference" cannot work. Clients must store the seed.
- **SpendActivity authorisation.** The owner authorises a move of its node through its own proposal action in the same transaction, not with a new signature. SubmitProposal needs the proposer's identity check and signature, WithdrawProposal the proposer's signature, AdoptProposal and RejectProposal the oracle, and ExpireProposal and ExpireStaleProposal only lower the count. A signature rule would block adoption, rejection and expiry without the proposer, and so lock the stakes of incorporated critiques. A first submission of another agent can spend a node or the head as the predecessor; it changes only `next_did`, and the entry keeps its address, tokens and AP3X.
- **The activity list head.** The deploy record transaction mints the `activity` record token with `params` and `oracle` and puts the head (`agent_did = #""`, count 0, `next_did = #""`) at the proposal_spend address (`scripts/deploy.py` step 5a). The token is one-shot, so there is one head. A redeployment of proposal_spend needs a new deployment, because the head stays at the old address.
- **Summed stake returns and one proposal action.** The stake return sums all outputs to the credential (`settlement.owner_paid`), and a transaction has one proposal action. The sum covers a proposal, critiques and endorsements of one credential in one transaction. The one-action rule keeps the activity count and the proposal mint set exact.
- **Exact token rules.** `critique_mint` checks the exact minted names itself. `proposal_mint` requires the one proposal action, and that action fixes the exact set of minted and burned tokens under the proposal policy. A burn needs no rule in the policies: only a spend of the UTxO that holds a token releases it.
- **Endorsement validator in CrossRefs.** `GovernanceCrossRefs` gets `endorsement_validator_hash` as field 5. Without it, `critique_mint` could not see endorsement inputs, so an endorsement could not mint or burn its token without a critique input.
- **Withdrawals do not change.** WithdrawCritique still needs an active proposal reference input and the critic's signature; it does not read `proposal_ref`. A critique whose proposal ended without it can still exit. WithdrawEndorsement needs only the endorser's signature.
- **Direct lineage only.** The parties rule compares direct parents. Deeper ancestry is not compared.
